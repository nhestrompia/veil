# Child-frame visibility actions

One fresh matched comparison per frame type tested ordinary visibility listeners inside same-origin, cross-origin, and srcdoc child documents. Each listener armed after the initial accepted form task.

Every candidate recorded two new actions: one during hide and one during restore. The helper posted no input and made no Accessibility call during those cycles. The application admitted zero keyboard events.

All three readable controls, private baselines, and resumed private tasks passed. All temporary cleanup checks passed. Aggregate Secure Input was off afterward. These results concern ordinary diagnostics, not the incomplete custom engine or a physical-human control.

Together with the focus controls, these tests show that top-document filtering alone cannot support the general-web action claim. The future custom-engine comparison must include child lifecycle events. It must also preserve native password ownership and private input after return.
