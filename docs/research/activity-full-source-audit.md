# Full-source audit of stable page activity

Audit date: October 26, 2026. Source: pristine local WebKit revision [`94f9b7905e3ce9a3d7497f26b563adcad6b7525f`](https://github.com/WebKit/WebKit/commit/94f9b7905e3ce9a3d7497f26b563adcad6b7525f). Reviewed patch: [stable-page-activity.patch](../../engine/patches/stable-page-activity.patch). This was a read-only source audit. No framework build or runtime verification occurred.

**Result:** The patch covers the discovered macOS WKWebView activity IPC sender and shared creation path. It does not fence independent DOM element focus operations. Initial empty-document creation also precedes projection into WebCore. Neither point alone disproves the scoped activity-IPC policy. They limit broader claims about all focus events or all possible startup script.

The patch passed `patch --dry-run -p1` against the pinned source, without rejected hunks. No decisive source-level build blocker emerged. A dry run does not verify compilation, framework loading, or behavior.

## Initialization order and script boundary

The first WebCore activity state is its constructor default: visible and in-window. `WebPage` retains the creation parameter at line 726. It creates WebCore `Page`, initializes the main frame, then applies retained activity at line 1158. The WebPage IPC receiver is registered afterward, at line 1190. Thus ordinary later navigation messages reach an already initialized activity state. [Page.cpp:356](https://github.com/WebKit/WebKit/blob/94f9b7905e3ce9a3d7497f26b563adcad6b7525f/Source/WebCore/page/Page.cpp#L356), [WebPage.cpp:726](https://github.com/WebKit/WebKit/blob/94f9b7905e3ce9a3d7497f26b563adcad6b7525f/Source/WebKit/WebProcess/WebPage/WebPage.cpp#L726), [WebPage.cpp:1158](https://github.com/WebKit/WebKit/blob/94f9b7905e3ce9a3d7497f26b563adcad6b7525f/Source/WebKit/WebProcess/WebPage/WebPage.cpp#L1158).

However, main-frame initialization already creates an initial empty document. `WebFrame::initWithCoreMainFrame()` calls `LocalFrame::init()`, which calls `FrameLoader::init()`. That function starts an empty-document load. Initial-empty user-script injection is gated by `ShouldInjectUserScriptsInInitialEmptyDocument`, whose default is false. [WebFrame.cpp:163](https://github.com/WebKit/WebKit/blob/94f9b7905e3ce9a3d7497f26b563adcad6b7525f/Source/WebKit/WebProcess/WebPage/WebFrame.cpp#L163), [FrameLoader.cpp:422](https://github.com/WebKit/WebKit/blob/94f9b7905e3ce9a3d7497f26b563adcad6b7525f/Source/WebCore/loader/FrameLoader.cpp#L422), [LocalFrame.cpp:797](https://github.com/WebKit/WebKit/blob/94f9b7905e3ce9a3d7497f26b563adcad6b7525f/Source/WebCore/page/LocalFrame.cpp#L797), [Settings.yaml:297](https://github.com/WebKit/WebKit/blob/94f9b7905e3ce9a3d7497f26b563adcad6b7525f/Source/WebCore/page/Settings.yaml#L297).

**Assessment:** Normal fetched-page script follows the projected constructor state. The source does not support the stronger statement that projection precedes every empty document or every optional injected script. This audit did not establish an untrusted script exploit during construction.

## Focus routes outside the activity projection

`WebViewImpl::becomeFirstResponder()` requests an activity update, restores editable selection, and can separately send `SetInitialFocus`. The latter depends on key-view selection direction. Its receiver clears the focused element and advances focus even when no valid keyboard event exists. Only the optional keyboard-event branch checks validity. These operations can produce DOM element focus changes without changing the projected activity bits. [WebViewImpl.mm:1622](https://github.com/WebKit/WebKit/blob/94f9b7905e3ce9a3d7497f26b563adcad6b7525f/Source/WebKit/UIProcess/mac/WebViewImpl.mm#L1622), [WebPage.cpp:4747](https://github.com/WebKit/WebKit/blob/94f9b7905e3ce9a3d7497f26b563adcad6b7525f/Source/WebKit/WebProcess/WebPage/WebPage.cpp#L4747).

Cross-process `ElementWasFocusedInAnotherProcess` and `FrameWasFocusedInAnotherProcess` also update element/frame focus separately. `RestoreSelectionInFocusedEditableElement` restores selection appearance when selection is absent. These are not alternate assignments to `WebPage::m_activityState`. [WebPage.cpp:10534](https://github.com/WebKit/WebKit/blob/94f9b7905e3ce9a3d7497f26b563adcad6b7525f/Source/WebKit/WebProcess/WebPage/WebPage.cpp#L10534), [WebPage.cpp:6761](https://github.com/WebKit/WebKit/blob/94f9b7905e3ce9a3d7497f26b563adcad6b7525f/Source/WebKit/WebProcess/WebPage/WebPage.cpp#L6761).

WebCore exposes direct activity setters on `Page` and `FocusController`. Testing `Internals::updatePageActivityState()` bypasses UIProcess projection. The direct Accessibility `setFocused(true)` activity write found in WebCore is iOS-only. The macOS branch instead requests native first respondership. Testing internals and injected bundles must remain outside the untrusted website surface. [Internals.cpp:6992](https://github.com/WebKit/WebKit/blob/94f9b7905e3ce9a3d7497f26b563adcad6b7525f/Source/WebCore/testing/Internals.cpp#L6992), [AccessibilityObject.cpp:3601](https://github.com/WebKit/WebKit/blob/94f9b7905e3ce9a3d7497f26b563adcad6b7525f/Source/WebCore/accessibility/AccessibilityObject.cpp#L3601).

The patch fixes five activity flags. It preserves other native flags, including visual idleness and hardware-console connection. It does not claim that every native lifecycle effect or observable timing signal becomes constant.

**Ownership distinction:** `m_inSecureInputState` is WebKit's bookkeeping flag. The code does not check the enable/disable calls' return statuses. Therefore even that private readback is not proof of successful OS protection. `IsSecureEventInputEnabled()` instead reports aggregate state; another owner can keep that state enabled.

**Actual eligibility and timing:** Update checks window key state and view focus. It does not check actual foreground PID. The patch preserves these native getters, unlike the earlier stable-window diagnostic. Source ordering alone does not prove protection before the first returned password key. Unchanged password focus may not trigger the editor-state condition. A frame commit can reset protection afterward. Those facts require ownership and aggregate measurements during return, navigation, and resumed input.
