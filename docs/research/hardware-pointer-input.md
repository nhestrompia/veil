# Hardware pointer input

Research date: 2026-10-28. This is a design review, not a physical-input test. It uses Apple's public documentation and published IOHIDFamily source, plus this repository's prior evidence. No device was opened and no input was sent for this review.

## Decision

A narrow experiment is feasible for a measured physical mouse with relative X and Y reports and a primary button. It needs its own application-owned pointer position, drawn in the browser, and an independently verified device ancestry. The current keyboard allowlist recognizes one measured built-in keyboard chain; it does not establish a mouse policy. The root agent subsequently measured two mouse-interface class chains and report descriptors in a read-only audit. These identify candidate profiles, not successful physical controls. Physical report delivery remains unverified. See the [pointer audit](../evidence/hardware-pointer-source-audit.json). [Current policy](../../Sources/Browser/HIDSourcePolicy.swift), [prior registry audit](../evidence/hid-source-audit.json)

This design can reject the identified software routes under a stated OS and device configuration. It cannot prove that a human caused each admitted report, that a hardware device or driver is uncompromised, or that a trusted user intended the resulting page action. A programmable USB device, compromised driver, privileged software, or a real physical mouse operated by someone else is outside that proof. Binding by a button press is a bootstrap gesture, not attestation.

## What a callback proves

`IOHIDManagerRegisterInputValueCallback` delivers values from enumerated devices; Apple describes them as elements usually issued by interrupt-driven reports. An element is parsed report data, not an authenticated human action. A report callback supplies report boundaries and bytes, but still does not authenticate the producer. [Apple input-value callback](https://developer.apple.com/documentation/iokit/1438367-iohidmanagerregisterinputvalueca), [Apple report callback](https://developer.apple.com/documentation/iokit/3042788-iohidmanagerregisterinputreportw), [Apple report processing](https://developer.apple.com/documentation/hiddriverkit/iouserhideventdriver/handlereport)

Quartz events are a different layer. Apple documents both construction of a mouse event with a chosen location and posting it into the event stream. Do not admit an `NSEvent` or `CGEvent` based on timing near a HID callback, and never use `NSEvent.mouseLocation`, a `CGEvent` location, or the system cursor position as the click coordinate. A posted event or another device can change that state independently of the approved device. [Apple CGEvent](https://developer.apple.com/documentation/coregraphics/cgevent), [Apple event posting](https://developer.apple.com/documentation/coregraphics/cgevent/post%28tap%3A%29?changes=_2)

Raw reports are not a universal defense. Apple supports virtual HID devices that send reports. The published `IOHIDSystem` source also creates an `IOHIDPointingDevice` for the legacy HID-manager posting option, and the pointing shim calls `handleReport`. The prior keyboard experiments observed no raw values in their legacy posting trials, but that does not resolve pointer behavior or prove the report path impossible on this machine. [Apple virtual devices](https://developer.apple.com/documentation/corehid/creatingvirtualdevices), [Apple system posting path](https://github.com/apple-oss-distributions/IOHIDFamily/blob/main/IOHIDSystem/IOHIDSystem.cpp#L2992), [Apple pointing report path](https://github.com/apple-oss-distributions/IOHIDFamily/blob/main/IOHIDSystem/IOHIDPointingDevice.cpp#L401), [prior posting results](../hid-posting-findings.md)

Before binding, reject explicit virtual markers and virtual transport, known software ancestry including `IOHIDUserDevice` and an `IOHIDSystem`-provided pointing shim, and missing, malformed, ambiguous, or incomplete ancestry. Admit only a separately measured physical-mouse ancestry with the expected device and element properties. Examine all parents or fail closed on multiple parents. Retain the selected device identity and clear it on removal. Do not treat vendor, product, location, or transport strings alone as proof. The existing source review explains the entitlement and shim limits; its keyboard-specific FIFO prefix must not be copied as a mouse allow rule. [HID origin review](hid-origin-guarantees.md), [Apple object conformance](https://developer.apple.com/documentation/iokit/1514505-ioobjectconformsto)

## Minimal path

1. With existing input-monitoring access already granted, enumerate without seizing devices. Measure candidate service ancestry and descriptor-derived element properties. A later physical control must identify which candidate actually produces the intended mouse's reports. Refuse unknown sources. Do not request permission automatically.
2. Bind one eligible device during an explicit in-app setup state. Start the application pointer at a visible, deterministic position inside the permitted content area. Give the user a clear visual indication that this is the pointer used for clicks. The normal system cursor may differ and can move over other applications.
3. Accept only input elements belonging to that bound device and the intended mouse collection. Require Generic Desktop X and Y to be relative, and a primary button with a validated range. Apple defines relative values as changes since the last report and absolute values as positions based on a fixed origin. Reject unsupported or ambiguous descriptors. [Apple relative element API](https://developer.apple.com/documentation/iokit/1564129-iohidelementisrelative?changes=_2)
4. Integrate signed deltas with a documented gain in application-local points, clamp to the content bounds, and render the application pointer there. Do not derive motion from the system cursor. Avoid guessing macOS acceleration or assuming raw device counts equal display points. Test direction, scaling, bounds, high-density displays, and the user-visible target position.
5. Process motion and button state in a defined report order. Prefer validated report-level parsing for a supported descriptor so a report containing both movement and a button transition has one deterministic interpretation. If using element callbacks, prove ordering and grouping for the supported OS and descriptor; do not assume an input-value callback is one complete report. Reject malformed, truncated, unknown, and out-of-range reports. Pair a primary down and up from the same binding and generation; cancel on interruption. Dispatch only locally constructed events carrying the internal point through the existing one-shot event gate, and verify actual WKWebView behavior rather than assuming synthetic AppKit events reach web content.

Keep the first experiment to movement and primary click. Scroll, drag, double click, secondary buttons, modifier interactions, gestures, and accessibility need separate semantics and controls. No system event tap, device seizure, pointer disassociation, cursor warp, or global interception is needed. Nonexclusive observation means the physical mouse also moves the normal system pointer; the application pointer and target must be clear enough that a user can operate them without relying on that cursor.

Trackpads cannot be assumed to provide the same relative mouse reports. Apple distinguishes relative pointer, absolute pointer, and digitizer report handling; inspect the actual device descriptor and observed values rather than treating a contact coordinate as a mouse delta. Absolute contacts need contact identity, touch-down/up and lift handling, bounds and calibration, and a policy for gestures and multiple fingers. A direct mapping may jump on a new contact; differencing contacts without their lifecycle can produce false movement. Refuse such devices in the first mouse path. [Apple report handling](https://developer.apple.com/documentation/hiddriverkit/iouserhideventdriver/handlereport), [Apple absolute and relative pointer events](https://github.com/apple-oss-distributions/IOHIDFamily/blob/main/IOHIDFamily/IOHIDEvent.cpp)

## Focus, geometry, and target integrity

Frontmost and key-window checks are useful stop conditions, not proof of intent: other processes or system events can affect focus and window geometry. Never automatically regain authority merely because focus returns. On focus loss, deactivation, removal, sleep, permission loss, window move or resize, display changes, modal or navigation transitions, or uncertainty about report delivery, cancel pending presses, invalidate the active pointer session and require a fresh physical re-arm. Keep a generation counter so queued callbacks and releases from an old session cannot act in a new one. Serialize lifecycle changes and input handling on one execution context.

Keep the pointer in content-local coordinates and bind each press to the same window, content view, geometry generation, and target context through release. Convert coordinates with AppKit's view/window conversion APIs, accounting for flipped views and points versus backing pixels. A geometry or layout change between press and release must cancel the click. The page itself can change targets under a stationary pointer, so a stable window geometry alone cannot establish target intent. A hostile page or a script that changes layout remains a separate risk; a sensitive action may need its own trusted confirmation. [Apple coordinate conversion guidance](https://developer.apple.com/library/archive/documentation/GraphicsAnimation/Conceptual/HighResolutionOSX/APIs/APIs.html)

## Verification plan

First use deterministic offline tests with fabricated descriptors, reports, device snapshots, and lifecycle events. Cover source allow and refusal, multi-parent and incomplete ancestry, virtual and system-shim sources, signed relative axes, report IDs and lengths, mixed movement/button reports, duplicate and out-of-order transitions, clipping, coordinate conversion, generation invalidation, device replacement, and focus or geometry changes between down and up. Confirm that untrusted Quartz positions cannot influence the internal point. These tests exercise policy; fabricated inputs do not establish OS delivery or physical origin.

Then run a separately authorized, bounded experiment in a harmless local fixture. Record the OS build, binary hashes, permissions, device ancestry and descriptor characteristics without recording serial numbers or unrelated input. Establish a physical mouse positive control for movement and click at known fixture targets before judging attacks. Check the system cursor and application pointer can diverge without changing the action coordinate. Test focus loss, window movement and resize, removal and reconnect, and a held button across cancellation. The independent fixture should report actual target activation, not only an internal accepted-event counter.

Compare authorized CGEvent posting, both existing IOHIDPostEvent options, and an entitled virtual mouse that emits valid relative reports. For each, record API outcome, callback device identity and source decision, application pointer movement, and fixture action. Include a positive control showing that the virtual device actually emits reports to an observer; an entitlement failure, missing callback, or unsuccessful injection is inconclusive. If a software report reaches the allowed device identity or the action succeeds, the claimed boundary fails. Keep budgets and privileges explicit and repeat trials. The earlier posting results were keyboard-only and cannot substitute for these controls. [Saved posting evidence](../evidence/hid-posting-results.json), [virtual-device limitations](hid-origin-guarantees.md)

The published Apple source links point to mutable `main` and are not proof of binary equivalence to the tested macOS build. This review establishes neither a physical mouse profile nor an end-to-end browser click result.

## Historical static implementation review

This section describes the initial implementation before the fixes below. Current physical and attack results are in [the candidate findings](../hardware-pointer-findings.md).

A later read-only audit recorded two candidate mouse service chains and report descriptors, one FIFO and one USB. This supersedes the earlier statement that no candidate mouse topology had been measured. Neither has a physical input control yet. [Candidate audit](../evidence/hardware-pointer-source-audit.json)

The descriptor bytes are consistent with the pinned decoders if callback bytes include the report ID. FIFO report 2 has an ID byte, one button/padding byte, two signed 8-bit axes, and four constant bytes. USB report 1 has an ID byte, one button/padding byte, two signed 16-bit axes, and one wheel byte. The decoder refuses secondary buttons and nonzero wheel values. Apple source for the kernel path extracts the ID from the first byte for multiple reports and passes the original report onward. The user-space callback forwards the report and its length unchanged. Physical callbacks on the installed build remain unverified. [Apple kernel report path](https://github.com/apple-oss-distributions/IOHIDFamily/blob/main/IOHIDFamily/IOHIDDevice.cpp#L2188), [Apple user-space callback](https://github.com/apple-oss-distributions/IOKitUser/blob/main/hid.subproj/IOHIDDevice.c#L1785)

Apple's published manager registers the timestamped callback on each device. Its device callback supplies the `IOHIDDeviceRef` as sender, supporting the implementation's cast for that source revision. The API documentation itself describes sender only as the sending interface. This source evidence is not verification of the deployed binary. [Apple manager registration](https://github.com/apple-oss-distributions/IOKitUser/blob/main/hid.subproj/IOHIDManager.c), [Apple device callback](https://github.com/apple-oss-distributions/IOKitUser/blob/main/hid.subproj/IOHIDDevice.c#L1785), [Apple callback contract](https://developer.apple.com/documentation/iokit/iohidreportcallback)

The initial synchronous AppKit click dispatch had a security blocker. It sends mouse-down and waits for `sendEvent` to return before sending mouse-up. A native control may enter a nested tracking loop on mouse-down and fetch queued mouse-up or drag events directly, bypassing the application's `sendEvent` gate. A queued untrusted event can therefore affect or complete that tracking interaction, and the synthetic release may not be reached until the loop exits. Test native controls and WebKit separately and close this path before claiming complete event admission. [Apple mouse tracking](https://developer.apple.com/library/archive/documentation/Cocoa/Conceptual/EventOverview/HandlingMouseEvents/HandlingMouseEvents.html), [Apple event retrieval](https://developer.apple.com/documentation/appkit/nsapplication/nextevent%28matching%3Auntil%3Ainmode%3Adequeue%3A%29?changes=_10)

The initial callback also canceled on a report longer than 64 bytes before checking its source or report ID. The audited FIFO descriptor includes vendor input report 0x44 with a 1,751-byte payload. If delivered, that valid report can cancel pointer authority even though it is not a pointer report. Reports or errors from another matched device can also cancel before the bound-device check. Scope validation and cancellation to the selected device and pointer report; verify actual buffer and delivery behavior on the tested OS. [Current pointer router](../../Sources/Browser/DevicePointer.swift)

## Fixes after static review

The candidate subsequently added a queue gate and a private release event. Native AppKit tracking and the custom WebKit control pass with a queued untrusted release. Vendor report IDs are ignored before their lengths are checked. Source validation precedes unbound packet validation, and bound-device callback errors cancel before report-ID filtering. A second Terra test exposed retargeting during small motion; the click now retains the physical press coordinate. These fixes do not replace the remaining physical and external controls. See [the candidate findings](../hardware-pointer-findings.md).
