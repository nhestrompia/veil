# Process-signal boundary

Checked 2026-10-26 on macOS 26.6. This research explains the measured [content-pause result](../engine-process-pause-findings.md). It does not establish prevention on a release browser.

Apple's `kill(2)` manual describes matching user IDs as a basis for signal permission. Its `sigaction(2)` manual states that a process cannot catch, ignore, or block SIGSTOP. Therefore a handler inside the paused renderer cannot reject that signal. [Apple kill manual](https://developer.apple.com/library/archive/documentation/System/Conceptual/ManPages_iPhoneOS/man2/kill.2.html), [Apple sigaction manual](https://developer.apple.com/library/archive/documentation/System/Conceptual/ManPages_iPhoneOS/man2/sigaction.2.html).

Apple describes Hardened Runtime protections against code injection, library hijacking, and memory tampering. That description does not establish a signal-denial guarantee. Milestone 89 measured successful pause/resume in a disposable Hardened Runtime command-line target, with its runtime flag verified. It also verified independent watchdog recovery. This result rules out signing alone for that control. It does not measure a hardened browser or every sandbox configuration. App Sandbox restrictions on the sender do not establish protection against every unsandboxed same-user agent. This last distinction is an inference. [Apple Hardened Runtime](https://developer.apple.com/documentation/security/hardened-runtime), [measured signing control](../signal-signing-findings.md).

Endpoint Security exposes `ES_EVENT_TYPE_AUTH_SIGNAL` for authorization before a signal operation. The event identifies the target and signal number. This is a candidate enforcement boundary, not an implemented defense. Its exact coverage, default muting, failure behavior, and survival when its own service is interrupted require tests. [Apple signal authorization](https://developer.apple.com/documentation/endpointsecurity/es_event_type_auth_signal), [Apple signal event](https://developer.apple.com/documentation/endpointsecurity/es_event_signal_t).

The ordinary Endpoint Security client requires an Apple-granted restricted entitlement. Its documented errors include missing root privilege and missing user TCC approval. The installed Apple SDK also specifies Full Disk Access for `es_new_client`. Existing Input Monitoring or Accessibility grants do not supply these prerequisites. No extension, privileged service, or new grant was installed for this milestone. [Apple entitlement](https://developer.apple.com/documentation/bundleresources/entitlements/com.apple.developer.endpoint-security.client), [Apple client errors](https://developer.apple.com/documentation/endpointsecurity/es_new_client_result_t), [Apple TCC error](https://developer.apple.com/documentation/endpointsecurity/es_new_client_result_err_not_permitted).

Apple also documents a macOS 27 descendants client without root or TCC requirements. It still needs the restricted entitlement. It receives events submitted or instigated by descendants. Do not assume it can deny an unrelated agent's signal merely because the target is a descendant. The current test Mac runs 26.6, so that API is unavailable here. [Apple descendants client](https://developer.apple.com/documentation/endpointsecurity/es_new_descendants_client(_:_:)).

The disposable signing control now confirms that an ordinary Hardened Runtime change leaves this signal operation available. A stronger design needs a tested operating-system boundary or a narrower threat model. A different renderer engine alone supplies neither. An Endpoint Security prototype needs a separate install plan, scoped policy, failure controls, and user approval before it runs. Test external sender coverage, service interruption, default muting, and false denials before any browser prevention claim. Clock virtualization remains an untested alternative with broader compatibility and adaptive-signal questions.
